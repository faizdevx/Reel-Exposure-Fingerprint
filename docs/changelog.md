- 2026-10-09: Security fixes for the four HIGH audit findings (H-1 to H-4), re-audit, and `docs/security-audit.md` updated. There were no CRITICAL findings. Each fix has regression tests and is described in `docs/security-audit.md`; the decisions are in ADR-005, ADR-013, ADR-019 (the three mechanisms stay Proposed or as before, now implemented) and the new ADR-024 (Proposed). **H-1, rate limiting (`server/app/ratelimit.py`):** token buckets in process memory, charged where a credential is accepted (`auth_deps.py`) and by a router guard for every `/api/` request. Ingest 60 a minute with burst 20 per user (ADR-005), events and frames separately, so more tokens buy nothing; other extension requests 30, dashboard 300, every `DELETE` 10, every `/api/` request per client address 600, login and register 20 per address, failed logins per email 5 then one attempt every 3 minutes, checked before any password work and identical for unknown emails; at most 4 argon2 operations at once (503 `busy`). `429` carries `Retry-After`. The client address believes `X-Forwarded-For` only from `REF_TRUSTED_PROXIES` and reads it from the right. nginx has `limit_req`. The extension parses `Retry-After`, never waits less than its own backoff, caps the wait and keeps its queue. All values are settings (`.env.example`). **H-2, request size (`server/app/body_limit.py`, `main.py`):** every route under `/api/` has a body limit (16 KB default, 800 KB frames, 1 MB hard ceiling on events with the exact 256 KB still applied after authentication so the 401, 403, 413 order holds). The 413 is now decided by the middleware, because FastAPI turns a body error into a 400; found by test. Validation errors are `{loc, type}` only (a 5 MB request used to be reflected in full, with passwords and invite codes); nginx `client_max_body_size 1m`. **H-3, the Reel cache is per user (ADR-024, migration `0006`):** `content_features` and `topic_assignments` start their key with `user_id` and cascade on user delete; the migration copies existing rows to every user with an exposure of the Reel (stored snapshots still replay; a test on a real downgrade and upgrade; found by that test: the old key had to be dropped before copying) and drops unowned rows. The worker, fingerprint loader, topic evidence, deletion and the prediction topic universe (`universe_for` now takes the user: a second path by which one user could change another's predictions) read only the user's rows. Deletion of one user never touches another's cache rows. Departs from spec §9, §12 and ADR-007; the spec was not edited. **H-4, hosted mode and TLS:** `docker-compose.hosted.yml` (Caddy, production, secure cookies, only ports 80 and 443 public, `REF_DOMAIN` required) and `Caddyfile` (HSTS, `nosniff`, framing and referrer headers, 1 MB cap); the API refuses to start with `REF_ENVIRONMENT=production` and `REF_COOKIE_SECURE=false`; the extension's server address is fixed at build time (`VITE_REF_API_BASE`), the build fails for plain HTTP to any host but loopback, and the manifest asks for that server only (`extension/src/api-base.ts`). CI validates the hosted override, its refusal without a domain and `nginx -t`. **Not verified:** hosted mode has not been run against a real domain. **Verified by hand:** nginx in the real `nginx:1.27-alpine` image in front of a stand-in API (2 MB body 413, 800 KB passes, 300 parallel requests gave 94 `429`s); that run also showed that in local mode a client on the machine can choose its own rate-limit address (audit L-13). **Tests:** `test_rate_limit.py` 31, `test_body_limits.py` 29, `test_cache_isolation.py` 9, `test_hosted_config.py` 13, extension `api-base.test.ts` and new cases in `api-client.test.ts` and `scheduler.test.ts`; existing tests changed only where the old behaviour was the finding (cache rows now carry a user; the shared-cache deletion test became a per-user one; `universe_for` takes the user; table-set guards list the new key). **Re-audit:** CRITICAL 0, HIGH 0 (was 4), MEDIUM 10 (open, out of scope), LOW 14 (3 new: L-12 an email can be kept locked, L-13 the local-mode address key, L-14 hosted mode untested). Re-run probes: the 20 MB login body is 413 in 0.12 s, the 5 MB request's response is 31 bytes, 200 rapid logins produce 429s. Also: the tests' lint configuration now ignores only test-appropriate rules (fake passwords, seeded random, long literals, look-alike Unicode fixtures), and type errors in the tests I wrote were fixed; 31 older type errors in eight test files remain (none in security code). Not done: the MEDIUM findings, `gh` issues (no GitHub access; drafts in `docs/security-issues/`, all marked fixed).
- 2026-10-09: Deterministic fingerprint replay; details in `docs/replay.md`. `python -m app.manage replay-fingerprint --pipeline-version FP [--user UUID] [--from DAY] [--to DAY] [--rel-tol] [--abs-tol] [--json]` rebuilds both fingerprints, the session snapshots and the daily snapshots from the stored assignments and compares each with the stored snapshots, read-only (`server/app/fingerprint/replay.py`). Inputs come from the provenance stored in the snapshots (assignment version and every fingerprint parameter), which must hash back to the requested version; missing, inconsistent, unreadable or non-matching provenance is an error, not a guess. Compared per snapshot: `taken_at`, `n_reels`, Reels in the bucket, last observation time, provenance, and every raw weight and share per topic; a snapshot on one side only, or a topic on one side only, is a difference. Floats match within `rel_tol = 1e-9` / `abs_tol = 1e-12`; NaN never matches; the largest differences are reported even on a match. The replay also rebuilds in reverse Reel order and reports `deterministic`. `--from/--to` (UTC days, inclusive) limit what is compared, not what is replayed. Exit 0 match, 1 mismatch, 2 could not replay. A stored distribution that no longer sums to 1 is reported as `inputs_rejected_by_engine` instead of crashing. Found while testing: `app/manage.py` ran `main()` before the new functions were defined (the `__main__` guard was above them); moved to the end. Tests: `test_replay_compare.py` 31 (pure: tolerance edges, hand-computed 1/3 and 2/3 case, every compared field, one-sided snapshots and topics, NaN, window, capped details) and `test_fingerprint_replay.py` 39 (pgvector: match after rebuild, parameters from provenance with a non-default half-life, read-only, ties at one instant, unassigned Reels, a changed weight, `n_reels`, `taken_at`, assignment, dwell, an added and a deleted Reel, missing and extra rows, windows, unreadable provenance, user and version isolation, command exit codes and output with no content, JSON, custom tolerance, bad arguments, and three fresh processes with different `PYTHONHASHSEED` giving identical output). Real run on the seeded demo database: 44 snapshots, 880 values, `max_abs_difference` 0, `deterministic` True; after setting one stored weight to 99 the command exits 1 and names `exposure day 2026-09-20 raw[1]: stored=99.0 replayed=1.918`.

- 2026-10-09: Next-topic prediction (spec §5.2, F12, §10, M6); details in `docs/prediction.md`. Five models in `server/app/prediction/`: `uniform`, `most_frequent` (add-one smoothed topic counts), `decayed_fingerprint` (exposure fingerprint shares), `markov` (add-one smoothed row of the last topic, falling back to the fingerprint while the row has fewer than 20 observations or there is no last topic) and `hybrid` (`lambda * P_fingerprint + (1 - lambda) * P_transition`, same fallback; `lambda` chosen walk-forward from the cumulative log loss on earlier Reels, default 0.5 until 100 Reels). The feature is named "Predicted next observed topic" in the API and the dashboard, and is never described as predicting preference. **Stored before the next event:** the replay predicts each Reel from the state before it and only then applies it; tests check that a stored prediction equals the prediction from the earlier Reels alone, that changing a Reel never changes its own prediction, and that a rebuild never rewrites earlier rows. `predictions` gets one row per Reel and model; `topic_transitions` the user's transition counts; new table `prediction_state` (migration 0004, with an index on `predictions (user_id, pipeline_version)`) holds the prediction for the Reel that has not happened yet and the evaluation summary, so `GET /api/v1/predictions/next` reads one row and never scans history. `pipeline_version` of predictions is `pr1-...`, a hash of every setting and the fingerprint version. **No success is claimed:** the evaluation is `complete: false` with no comparison and no verdict until 1,500 Reels are scored; after that the hybrid is compared with each other model by cluster-bootstrap intervals over sessions, and `hybrid_beats_required_baselines` is true only when its log loss is clearly lower than both required baselines. Dashboard: a "Predicted next observed topic" panel on the first page (distribution adding up to 100%, why the fingerprint stood in when a row is short, an evaluation banner, and a table of all five models with rolling and all-time figures). `python -m app.manage rebuild-fingerprints` now also rebuilds predictions (`--skip-predictions` to leave them) and takes its topic ids from the stored topics. Deletion: `prediction_state` is deleted with the user, and session deletion now rebuilds predictions from the Reels that remain instead of leaving them deleted. Tests: `test_prediction_engine.py` 34, `test_prediction_evaluation.py` 12, `test_prediction_store.py` 21 (pgvector), Vitest 6 new, Playwright 22 runs; schema and deletion tests updated. Real-stack run on random seed data: five models, 122 Reels scored, evaluation shown as not complete; none of the models beat the simple baselines there, as expected for random sequences. Not built: a job loop that rebuilds predictions on its own, the self-report survey, a half-life sensitivity run.
- 2026-10-09: Complete data deletion (spec F13, N7; implements ADR-012 and ADR-007 option 1 on the owner's request; both ADRs are still marked Proposed and should be accepted). `DELETE /api/v1/sessions/{id}` and `DELETE /api/v1/me/data` (dashboard login and the CSRF header; an extension token is not enough). **A session** goes with its Reels, their jobs, their frames, and everything derived from it: predictions and topic transitions (cumulative over the whole history, so deleted whole; M6's rebuild will regenerate them) and the user's fingerprint snapshots, which are then **rebuilt** from the Reels that remain using the settings each snapshot recorded in its provenance (snapshots without provenance cannot be rebuilt and are dropped, and the report says so). **Delete all** removes every row of the user in every table (sessions, exposures, snapshots, transitions, predictions, consent, tokens, dashboard logins, used invites, jobs) and the whole frame folder, then the account last. **Shared Reel cache** (`content_features`, `topic_assignments`): every row no exposure of any user refers to is swept, so zero rows remain once nobody has the Reel, and a Reel another user still watched keeps its row with no link to the deleted user. **Verified, not assumed:** after the rows and files are deleted a fresh pass counts what is left in each table and on disk; the call answers 200 only when every count is zero, with the counts in the report, and 500 `deletion_incomplete` with what is left otherwise. For delete-all the account (and so the login) is deleted only when everything else verifies clean, so a failed deletion can be retried by the same user; the files are deleted after the database commit, and a failing file step shows up as files left. **Idempotent and self-healing:** a session that is gone or not yours answers 200 `existed: false` and touches nothing of anyone else's (no existence oracle); a retry also clears what an earlier failed attempt left for that user (frame folders no existing event owns, exposure jobs whose exposure is gone, unreferenced cache rows). After a successful delete-all the login no longer exists, so a repeat is 401. **Consent revocation** already stopped every active session (`stop_reason=consent_revoked`) and refuses further events and frames; it does not delete data (a test says so). Dashboard: a "Delete session" button on every session with an inline confirmation that names what goes, and an Account page (`/account`) with the list of what is removed, a typed `DELETE` confirmation, and the verified result; an unfinished deletion is shown as unfinished with what is left and a retry. Tests: `test_deletion.py` 28 (every table counted independently, a guard that fails when a table is added without being accounted for, other users untouched, authorisation and CSRF, idempotence, and deliberately broken deletions: files that quietly survive, a failing file step, a skipped cache sweep, surviving jobs, each of which must be reported as not done and finish on retry), Vitest 4 new, Playwright 20 new. - 2026-10-09: Topic evidence (spec F11, §8). `GET /api/v1/topics/{topic_id}/evidence?kind=exposure|engagement&limit=&offset=` (dashboard login; `limit` 1 to 100, default 20; `offset` 0 or more) lists the Reels that put a topic into the user's current fingerprint, biggest contribution first, with `total`, `next_offset` and the page. **Why it is there:** a fingerprint weight is the sum over Reels of `topic score x gain x recency` (the engine's update rule unrolled), so each item carries its fused topic score (and the text and visual scores), its gain (exposure 1; engagement by dwell), its recency factor (0.5 per half-life), its contribution, and its share of the topic's weight; the response also gives the topic's weight, the total weight, the share shown on the dashboard, the half-life, the gain rule in words, and `coverage` (the sum of all contributions divided by the stored weight, 1.0 when the list explains the whole weight). Each item also has the Reel link (`https://www.instagram.com/reel/<shortcode>/`), caption (cut at 300 characters, marked), observed time, dwell and video length (null stays null). **How it stays exact:** snapshots now record `provenance` (the assignment version they read and the fingerprint parameters), so evidence is computed from the same rows and numbers the fingerprint used, not today's settings; the contribution is evaluated in SQL so ordering and paging are exact over all of a user's Reels without loading them (fixed number of queries; tests hold the SQL to the engine's own `engagement_gain` and `decay_factor`). A snapshot without provenance, a user without a fingerprint and a topic with no weight get 200 with a `reason` and no items; an unknown topic id is 404. **Authorisation:** the user comes from the login cookie only; every query starts from that user's own exposures (assignments are shared by Reel and reached only through them), so another user's Reels, captions and ids cannot appear. **Dashboard:** every topic row of the two fingerprint cards is a button that opens a side panel ("Why Cricket is in your exposure fingerprint"): a summary (share, weight, how Reels count, half-life, how much of the weight the list explains and how much the five biggest contributors account for), then the Reels with link, caption, observed time, dwell, scores, gain, recency, contribution and share, paged ten at a time with Previous and Next. Escape, Close and a click outside close it and focus returns to the topic. The folded "N other topics" row is not clickable. Tests: `test_topic_evidence.py` 34 (login, user from cookie, another user's Reels never present, ids never present, reconciliation with the stored weight for both kinds and three topics, parity with the engine, recency, skipped Reels, versions, paging edges and stable ties, queries constant, read only), Vitest 5 new, Playwright 15 new (30 runs). Not built: evidence from the History page's comparison table, a per-session view.

- 2026-10-08: Frame upload, `POST /api/v1/events/{event_id}/frames` (spec F7, F15, §8). - 2026-10-08: Fingerprint engine (`server/app/fingerprint/`), spec §5.2 and F10. Exposure and engagement fingerprints as topic-weight vectors (not centroids): `W_k <- W_k * 2^(-dt/h) + g * p(k)`, half-life 7 days, display `W_k / sum(W)`. Exposure `g = 1`; engagement `g = clip(dwell / max(duration, 5 s), 0.1, 2.0)`, dwell under 1.5 s gives 0.1. `dt` comes from `observed_at`. `rebuild` is the one replay function: input order does not matter, ties break by `event_id`, and it emits one snapshot per session and kind (`taken_at` is the last Reel's `observed_at`, never the wall clock). `fingerprint_version` (`fp1-...`, a hash of the parameters and the upstream assignment `pipeline_version`) is stored on every snapshot. Snapshot JSON holds the raw weights (to resume) and the share. Missing data: a Reel with no assignment is skipped by both fingerprints, a Reel with no dwell by engagement only; skipped Reels change nothing. OPEN: a missing video duration uses the 5 s floor of the formula; owner to confirm. Not built: job loop, per-user state table (ADR-011 Proposed), daily snapshots, ADR-008 version split.
